# Agentic Workflow

A basic AI pipeline that takes a ticket from idea to a draft PR. You decide **what** to build and **whether** the result is good enough; the AI does the work in between.

```
/start-ticket PROJ-123 "..."
  → Triage (questions + gate check before any changes)
  → ticket.md → context.md → plan.md
  → ⏸ YOU APPROVE THE PLAN
  → Implementer writes code + tests (quick gate)
  → Reviewer checks the diff against the plan
  → Orchestrator runs the full gate → approve or send back (max 2 rounds)
  → pr.md (commit message + PR description) → YOU review, commit and push
```

## Roles

| Role         | Who                                        | Model                           | Job                                                |
| ------------ | ------------------------------------------ | ------------------------------- | -------------------------------------------------- |
| You          | Human                                      | —                               | Answer triage, approve the plan, review and commit |
| Orchestrator | Your main Claude Code session              | Whatever you pick with `/model` | Plans, delegates, runs the final gate, decides     |
| Implementer  | Subagent (`.claude/agents/implementer.md`) | Sonnet, high effort             | Writes code and tests                              |
| Reviewer     | Subagent (`.claude/agents/reviewer.md`)    | Opus, xhigh effort              | Reviews the diff; writes only its review           |

## Files

| Path                                 | What it is                                                 | In git |
| ------------------------------------ | ---------------------------------------------------------- | ------ |
| `.ai/skills/start-ticket/SKILL.md`   | The `/start-ticket` command                                | ✅     |
| `.ai/skills/start-ticket/flow.md`    | The rulebook the AI follows (steps, roles, file templates) | ✅     |
| `.ai/skills/commit-msg/SKILL.md`     | The `/commit-msg` command for commits outside the pipeline | ✅     |
| `.claude/agents/implementer.md`      | Implementer subagent                                       | ✅     |
| `.claude/agents/reviewer.md`         | Reviewer subagent                                          | ✅     |
| `.ai/scripts/gate.sh`                | Runs all quality checks with a compact summary             | ✅     |
| `boost.json`                         | Laravel Boost config; used to regenerate the AI setup      | ✅     |
| `.ai/work/<ticket-slug>/`            | Handoff files for each ticket (scratch work)               | ❌     |
| `.claude/skills/`, `.agents/skills/` | Copies generated by Boost — do not edit                    | ❌     |

## One-time setup (each developer)

```bash
composer install            # also runs boost:update
php artisan boost:update    # generates AGENTS.md, skills, MCP config from boost.json
vendor/bin/sail up -d       # start Sail; tests need its MySQL database
```

Then restart Claude Code so it loads the `/start-ticket` command and the agents.

## Working on a ticket

### 1. Start clean and create a branch

Commit or stash unrelated changes first. Anything uncommitted gets mixed into the ticket's diff.

```bash
git status                                  # should be clean
git checkout -b feature/PROJ-123-member-since-date
```

The orchestrator saves the starting state to `.ai/work/<ticket-slug>/git-start.txt` and warns you if it isn't clean. At the end it checks that only the ticket's files changed and that no agent touched git state (staging, stashing, committing).

### 2. Pick the orchestrator's model

```
/model     e.g. Fable 5.1 or Opus 5.5
/effort    e.g. medium
```

### 3. Start the ticket

```
/start-ticket PROJ-123 show "Member since" on the profile page   ← Jira
/start-ticket #45 fix login redirect loop                         ← GitHub issue
/start-ticket tidy up the dashboard spacing                       ← no ticket
```

Always put the request on the same line. Running `/start-ticket` alone just asks you for it.

### 4. Answer the triage questions

The orchestrator first runs the full gate to confirm the project is clean, then asks a few questions about scope and acceptance criteria. Be specific — vague answers make vague plans.

### 5. Review the plan ⏸

It writes `ticket.md`, `context.md` and `plan.md` to `.ai/work/<ticket-slug>/`, shows a summary and **stops**.

- `approved` — the rest runs without you
- `change step 1: ...` — it updates the plan and asks again

This is the cheapest place to catch a misunderstanding. Read `plan.md` in full for anything non-trivial.

### 6. Let it run

The implementer and reviewer run automatically, up to 2 rounds, followed by the full gate. Approve permission prompts for commands like `.ai/scripts/gate.sh` and `vendor/bin/sail artisan test`, or allow them permanently.

### 7. Review the result

```bash
git diff                                   # the actual code
cat .ai/work/<ticket-slug>/review-*.md     # what the reviewer found
cat .ai/work/<ticket-slug>/pr.md           # commit message + PR text
```

Also check the feature in the browser (`vendor/bin/sail up -d`, then `vendor/bin/sail npm run dev`).

### 8. Commit and open the PR yourself

The pipeline never commits or pushes. Use the commit message, PR title and description from `pr.md`.

## Ticket references

| You pass   | Work folder                            | Commit / PR                                            |
| ---------- | -------------------------------------- | ------------------------------------------------------ |
| `PROJ-123` | `.ai/work/PROJ-123-member-since-date/` | `feat: PROJ-123 ...`, trailer `Refs: PROJ-123`         |
| `#45`      | `.ai/work/GH-45-login-redirect-loop/`  | `fix: ... (#45)`, `Closes #45` (auto-closes the issue) |
| nothing    | `.ai/work/dashboard-spacing/`          | No ticket parts                                        |

The AI never invents a ticket number.

## The gate

`.ai/scripts/gate.sh` runs the project's checks and prints one line per check. Full logs go to `.ai/work/.gate/<check>.log`; long failure output is cut to 15 lines of up to 800 characters.

Pint, Larastan, JS lint and TypeScript run on the host. Pest runs inside Sail because it needs the MySQL database, so **Sail must be running** (`vendor/bin/sail up -d`). If it isn't, the gate fails with a message saying so.

```bash
.ai/scripts/gate.sh quick   # Pint (changed files), Larastan, Pest
.ai/scripts/gate.sh full    # + Pint (all files), JS lint/format, TypeScript
```

```
✅ pint
✅ js-lint
✅ typescript
✅ larastan
✅ pest
GATE (full): PASSED
```

It exits with `0` on pass and `1` on failure. You can run it yourself at any time.

## When things go wrong

| Situation                                  | What to do                                                                                   |
| ------------------------------------------ | -------------------------------------------------------------------------------------------- |
| Stopped after 2 rounds with open issues    | Read `verdict.md`. Fix it yourself, or ask for one more round focused on the issue.          |
| You don't like the result                  | `git checkout . && git clean -fd` (or delete the branch) and restart with a clearer request. |
| Session was compacted or Claude was closed | Say: "continue the start-ticket flow for `.ai/work/<ticket-slug>/`".                         |
| The gate fails before you start            | Fix the existing failures first, or the pipeline cannot tell new failures from old ones.     |
| The request is too big                     | Split it. One ticket should be one reviewable PR.                                            |

## Commit messages outside the pipeline

For commits that don't come from `/start-ticket` — fixes after PR review, small changes without a ticket, manual work — use `/commit-msg`:

```bash
git add <files>          # stage what you want to commit
```

```
/commit-msg
/commit-msg fix review feedback      ← optional hint
```

It reads the staged diff, takes the ticket reference from the branch name (`feature/PROJ-123-...` → `PROJ-123`, `fix/GH-45-...` → `#45`), drafts a message in the same format as `pr.md`, and commits only after you confirm. It never stages, amends or pushes.

## Housekeeping

`.ai/work/` grows with each ticket. It is local scratch work — once the PR is merged, everything worth keeping lives in Jira/GitHub, the PR and git history.

```bash
rm -rf .ai/work/PROJ-123-member-since-date                              # one ticket
find .ai/work -mindepth 1 -maxdepth 1 ! -name .gate -exec rm -rf {} +    # all tickets
```

## Changing the workflow

- Edit the source files in `.ai/skills/start-ticket/`, never the copies in `.claude/skills/` or `.agents/skills/`.
- Run `php artisan boost:update` afterwards to sync the copies.
- Agent models and instructions live in `.claude/agents/*.md`.
- Restart Claude Code to pick up changes.
- The subagents are Claude Code only. Codex gets the `/start-ticket` command but not the implementer/reviewer agents.
